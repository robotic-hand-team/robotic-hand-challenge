# AGENTS.md

Hackathon repo (Black Forest Hackathon 2026): estimate the pose and slip of a grasped object from the tactile sensors on an Inspire RH56DFTP hand. The full brief is in `docs/internal/challenge_description.md`.

## What actually exists (don't trust the scaffold)
- `backend/`, `emulator/`, `frontend/` are **empty stubs** — except `frontend/public/hand.png`, which is a real image (a line drawing of the hand that `hardware/tools/hand_gui.py` uses as its heat map background, and `hand_sim/tactile_panel.py` uses as its silhouette). Every `src/*`, `Dockerfile`, `requirements.txt` and `package.json` is 0 bytes, and so is root `pyproject.toml`. `docker compose up` will not build. If a task needs one of these services, you have to write it from scratch.
- The only working code is:
  - `hardware/tools/hand_gui.py`: Tkinter slider control plus a tactile heatmap, talking to the real hand over Modbus TCP.
  - `hardware/logger.py`: `HardwareLogger` class that writes threaded JSONL logs. It is a library with no `__main__`.
  - `simulation/example/control_inspire_hand.py`: MuJoCo PD-control demo.
  - `simulation/hand_sim/`: grasp simulation that emulates the hand's registers, random handover episodes and a scripted grasp policy (see Simulation below).
- There are no linters, formatters or CI. The only tests are `simulation/hand_sim/test_smoke.py` (plain functions, run with `python -m hand_sim.test_smoke` from `simulation/`— pytest isn't installed and the venv has no internet access to add it).

## Environment
- Use the root `venv/` (Python 3.11 with mujoco 3.16, numpy 2.x, pymodbus 3.16, pillow, trimesh, coacd). Run things with `venv/bin/python`. Only the simulation has a requirements file (`simulation/requirements.txt`).
- On macOS, the MuJoCo viewer (`launch_passive`) must run under `venv/bin/mjpython`, not `python`: `venv/bin/mjpython simulation/example/control_inspire_hand.py`.
- The team's hand runs at `192.168.123.211:6000`, Modbus device id 1. This IP is hardcoded in the GUI, the logger and the dataset `meta.json`. `192.168.11.210`, used in `.env.example` and `hardware/register_map.json`, is the factory default from the manual, not this hand's address. `docker-compose.yml` gives the emulator port 5020 while `.env` says 6000, and nothing reads `.env` yet.

## Modbus / hardware gotchas
- The source of truth for hand registers is `docs/internal/hand_manual.pdf` (RH56DFTP user manual, PRJ-02-TS-U-010). It has the register table on p. 16–17 and the tactile layout on p. 26–27. The wrist manual is a separate PDF in the same folder.
- pymodbus 3.16 takes `device_id=`, not `slave=`. `hardware/logger.py` still passes `slave=1`, and its blanket `except Exception` hides the resulting `TypeError`, so it silently logs zeros. `hand_gui.py` uses the correct form.
- Register reads are chunked at 120 registers or fewer. Copy the `safe_read` pattern.
- `hardware/register_map.json` is **not valid JSON** because it contains stray `[cite: N]` annotations. Clean it before calling `json.load`. Its `size` fields are in **bytes**: a 3x3 tactile pad is `size: 18`, which is 9 registers. Code reads `rows*cols` registers.
- 6 DOFs. On the hardware and in the dataset, the order is `little, ring, middle, index, thumb_bend, thumb_rot`. The MuJoCo actuator order is different: `thumb_yaw, thumb_pitch, index, middle, ring, pinky`. Remap when converting between them.
- `1486` is `angle_set` (the commanded setpoint) and `1546` is `angle_act` (the measured angle). `logger.py` records 1486 as "joints", so it captures setpoints, not measurements.
- Angles run 0–1000, with 1000 = open. In physical terms: fingers 20°–176°, thumb bend −13°–70°, thumb rotation 90°–165°. `FORCE_SET` is the fingertip force in grams (0–3000); the finger stops moving once `FORCE_ACT` reaches it. Speed 1000 means a full stroke in about 600 ms. `ERROR` bits: 0 locked rotor, 1 over-temperature, 2 overcurrent, 3 motor fault, 4 comms. `STATUS` is at register 1612 (6 bytes, 1 per DOF). It's missing from `register_map.json` and the manual gives no meaning for its values. Inferred from the dataset: `0` = releasing/open (target ≥ actual), `1` = closing or holding at a closed target, `2` = stopped by the force limit while closing (force around 1900 g), `255` = only in session `20261016_201150`, where the hand wasn't moving (likely not initialised).
- Palm tactile data (8×14) is column-major and bottom-to-top: data point k is row `7 - k%8`, col `k//8`. Fingers are row-major. `hand_gui.py`, and the `palm_r*_c*` labels in the dataset, use a plain `reshape(8, 14)`, so the palm row/column labels don't match the physical layout.
- Tactile layout: 17 groups at registers 3000–4900. The same table appears in `hand_gui.py`, `logger.py` and every `meta.json`. Raw values are 0–4095. The tools subtract a per-taxel baseline recorded at startup and treat values above 50 as contact.
- Wrist registers (1020–1042, 100 units/deg) are documented in `docs/internal/wrist_module_relevant_information.md`. Nothing in the code uses them yet.

## Dataset (`models/dataset/<YYYYMMDD_HHMMSS>/`)
- Each session holds `actuators.csv`, `tactile_raw.csv` (`<group>_r<row>_c<col>`), `tactile_summary.csv` (per-group sum/max/contacts/centroid/force) and `meta.json` (sensor layout plus calibration `offsets`). Join the CSVs on `frame` or `t_unix`.
- `actuators.csv` has **two schemas**. The first two sessions (`20261016_201150`, `20261016_201443`) only have `angle_set_*`/`angle_act_*`/`force_act_*`/`current_*`/`error_*`/`status_*` (45 columns). Every later session (16 of 18) also has `pos_set_*`, `force_set_*`, `speed_set_*`, `pos_act_*` and `temp_*` (69 columns) — treat this as the current schema. `meta.json` gained a `sample_rate_target_hz` field at the same point.
- The recorder script that produced this data is **not in the repo**. `logger.py` writes a different JSONL format. The summary uses the same logic as `draw()` in `hand_gui.py`, checked against the data: values = raw minus baseline, clipped at 0. `contacts` = number of taxels above 50. `cy`/`cx` = mean row/column index of those taxels and `force` = their mean value, but only when contacts ≥ 2; otherwise both are blank and `force` is 0.0. Rounding: `sum` to an integer, `force` to 1 decimal, `cy`/`cx` to 2 decimals. About 5% of summary values differ by ±1 from what `tactile_raw.csv` gives, most likely because the summary was computed before the raw values were rounded.
- `models/dataset/logs/*.log` are CAD STEP-export logs, not sensor logs.
- The `.gitignore` rule `models/dataset/*.csv` only matches the top level, so the session subfolders are committed.

## Simulation
- `scene.xml` includes only the right hand; the left-hand files were deleted. The hand materials now live in `inspire_hand_right.xml`, because they used to be defined in the left-hand file.
- `hand_sim` must run from `simulation/` as a module: `../venv/bin/python -m hand_sim.assets` regenerates `simulation/objects/<id>/` from the STLs (mm → m, CoACD convex parts), and `../venv/bin/mjpython -m hand_sim.run` opens the viewer with terminal commands. MuJoCo's own viewer shortcuts use most letter and digit keys, so the viewer takes its commands from stdin instead.
- `scene.py` patches the vendor XML at load time through `MjSpec`; the XML itself still has the old torque motors and collisions off. The patches: hand collision geoms (group 2) get contype 2 / conaffinity 3 (**self-collision is on**), object hulls (group 3) get 1/3, the ground plane gets 4/1 so the hand still cannot touch it, and the torque motors become position servos per DOF, in register DOF order, named `act_<dof>`. Solver settings also come from `config.py`: `TIMESTEP` 1 ms, `iterations`/`ls_iterations` 100, `noslip_iterations` 15, and `CONTACT_SOLREF`/`CONTACT_SOLIMP` applied to every hand, object and ground geom.
- Hand self-collision needs `_exclude_adjacent_hand_bodies()` in `scene.py`, and the reason is non-obvious: `option.filterparent` is enabled in this build, yet MuJoCo **still generates contacts** between the palm and every finger's proximal segment — `mjDSBL_FILTERPARENT` is not set, so filtering is nominally on, but those pairs come through anyway. They overlap by 11-13 mm because the finger roots physically sit inside the palm volume. Resolved as real contacts they produce forces around **2.7 MN** (`right_hand_root` ↔ `right_thumb_proximal_base`) and every grasp fails (measured: 0/20, with objects hammered into the floor and the hand reading phantom `*_pad` tactile pressure). With the excludes added, hand-hand forces peak at ~43 N and grasps succeed. Contacts *between different fingers* — the ones that actually stop fingers passing through each other — are not excluded.
- The vendor collision geometry is **not** the drawing, and one part of it is far off. Measured against the drawn surface of the same body (`physics_audit.py --geometry-only`, which now reads the compiled model and samples *surfaces* rather than vertices): the fingers bulge up to **7.2 mm** (`thumb_proximal`; then 6.6 mm `thumb_intermediate`, 5.4 mm `thumb_proximal_base`, 4.4 mm `index_proximal`), the objects ~2.5 mm, and the **palm 18.3 mm**. The palm is the special case: it has no collision mesh at all, just 7 boxes and a cylinder, and boxes cannot follow a curved tapered palm — 391 of 1546 sample points on those primitives are more than 5 mm outside the drawn palm, confirmed by ray parity rather than by a normal-sign test alone. The `right_base_link.obj` sitting in `collision/` is unused and is an exact copy of the drawn palm mesh, so the drawn surface is already available as a decomposition input. Consequences: contacts fire earlier than the drawing implies, the inflated fingers can block each other before they visually touch, and `tactile.py` (which derives every patch from the group-2 geoms) places the patches on the inflated shape. Rebuilding all of it with CoACD on the drawn meshes is the outstanding geometry work. Every object collision part also exceeded the old `maxhullvert=64`, so `MAX_HULL_VERT` is now 256 (compile time is unaffected, well under a second).
- Never compare success rates between two configs without fixing the pose sequence. `HandoverEpisode` draws its handover pose from the rng it is handed and rejects candidates through `_path_clear`, whose rejection count depends on the geometry, so two configs drift onto different poses and their rates are not comparable. Hand each episode index `k` a fresh `np.random.default_rng([seed, k])` instead, then test paired (McNemar). This is what showed that the "the 38 dropped from 83% to 58%" claim was mostly sampling variance: at 150 paired episodes per object the 29 is unaffected (58% → 59%, p=1.000) while the 38 really does lose about 9 points (66% → 57%, orig-only 28 vs final-only 14, p=0.044).
- `physics_audit.py` (`../venv/bin/python -m hand_sim.physics_audit --episodes N`, `--geometry-only`, `--no-geometry`) is the physics acceptance test: solver settings, collision-vs-drawn surface deviation per body, penetration depth per contact category (hand-object / hand-hand / floor), hand self-intersection via `mj_geomDistance` (so it measures even while self-collision is off), and success rate. Run it before and after any physics change. It is how the timestep and contact-impedance values were chosen, and it is what caught the self-collision blow-up. Two things about its geometry report are deliberate and worth not "simplifying": it builds the model instead of reading the mesh files, so it reports the geometry actually in use (the palm's file next to the other collision meshes is unused, and a file-based comparison would score the palm as perfect while the model collides with boxes 18 mm proud); and it samples points over each surface — vertices, face centroids and edge midpoints — because a convex collision mesh spanning a concavity in the drawing has *all its vertices on* that drawing, so a vertex-only metric understates the bulge exactly where it matters (`thumb_intermediate` reads 1.6 mm vertex-only and 6.6 mm sampled). Both directions are exact point-to-triangle distances via `trimesh.proximity`, which works because `rtree` is installed.
- Hand frame: palm faces +x, fingers point +z, thumb is on the +y side. Joint position 0 = open = angle 1000 for every DOF, and thumb yaw at its maximum = opposed thumb.
- In `hand.py`, `FORCE_ACT` comes from contact torques about each DOF's joint divided by the fingertip lever arm, not from actuator torque, so free motion reads idle (77 g). `CURRENT` is still a placeholder model. Objects hang from a mocap "carrier" through a weld (`<id>_weld`); setting `eq_active = 0` releases them.
- Object masses in `config.py` are 0.25 kg for VEGABAR 29 (confirmed against its datasheet) and 0.6 kg for VEGABAR 38 (never verified). VEGABAR 38 must be grasped on its shaft next to the head, near its centre of mass, or it rotates out of the grasp.
- `episode.py` runs random handovers: a mocap "carrier" eases the object from a random pose/orientation into the open hand (`PHASE_APPROACH`), a `Policy` (`policy.py`) closes the fingers (`PHASE_GRASP`), then the carrier lets go and the hand holds alone for `HOLD_TIME_S` (`PHASE_HOLD`). `ScriptedGraspPolicy` is the baseline; `NNPolicy` is an unimplemented stub for the real model. `../venv/bin/python -m hand_sim.episode --episodes N` runs it headless and prints success rates; `mjpython -m hand_sim.run --demo` runs it in the viewer.
- The carrier-to-object weld (`eq_solref`) is deliberately **soft** (`CARRIER_WELD_TIMECONST = 0.1`), not rigid: a stiff weld fights the fingers while they close and the object gets flung out on release. `World.set_support()` cancels the object's weight only while it's carried, so the soft weld doesn't sag; `HandoverEpisode` ramps that support down over `RELEASE_RAMP_S` after release instead of cutting it instantly. Both choices came from measuring grasp success rate versus weld stiffness; don't "fix" the weld without re-running `hand_sim.episode` on both objects.
- With `ScriptedGraspPolicy`, success rates from `hand_sim.episode --episodes 200` are roughly 65-70% (VEGABAR 29) and 80-85% (VEGABAR 38). Most failures are the object rotating out of the fingers during closing, not drops after release; a smarter policy (sequencing fingers, or acting on tactile input once milestone 3 lands) should beat the scripted baseline.
- `episode.py` samples random handover poses by rotating/offsetting around each object's `pivot` point (`config.py`), not its mesh origin, and rejects poses whose approach path collides with the hand (up to `MAX_SAMPLE_TRIES`). Use `HandoverEpisode(..., randomize=False)` to start exactly at an object's nominal `grasp_pos`/`grasp_quat` for deterministic tests.
- `tactile.py` (17 sensor groups, `config.SENSOR_GROUPS`) derives each patch's position and size from the live mesh at startup, not from hardcoded millimetre numbers: a fixed local-axis convention per body category (finger / thumb / palm, in `config.py`) plus a `(start_frac, end_frac)` window along the body's row axis (0 = joint, 1 = fingertip). Those fractions were calibrated by sampling real contact points during many grasps (`calibrate_tactile.py`, a one-off dev tool, not needed at runtime) and are an approximation of the manual's sensor diagram (p.26), not a measured fact. Only 12 of 17 groups activate in typical power grasps (contact concentrates on the nail/mid segments); `thumb_tip`, `thumb_nail` and most `*_pad` groups rarely fire — this is the grasp style, not a bug.
- `recorder.py` writes sessions in the **current** (69-column) `actuators.csv` schema plus a ground-truth `object_pose.csv` the real hardware can't produce. `POS_ACT` is linearly fit from `models/dataset` (`pos_act ≈ -1.82 * angle_act + 1903`, ±108) since the manual marks it "not recommended" and gives no formula; `TEMP` is an untuned placeholder. `../venv/bin/python -m hand_sim.recorder --episodes N --out ../models/dataset_sim` runs it; `test_recorder_matches_real_dataset_headers` in `test_smoke.py` checks the headers against a real session and will catch drift if the real schema changes again.
- `simulation/simulation/` is an untracked duplicate copy. Ignore it, and don't edit it by mistake.
- The viewer has two tactile heat maps, both fed by `tactile.py` and refreshed at the sensor rate (20 Hz) inside `hand_sim/run.py`: `tactile_panel.py` draws a **thermal panel** (default) and `taxel_overlay.py` draws glowing tiles on the 3D hand (`--heatmap panel|3d|both|off`, `--heatmap-size`, `--heatmap-gain`, `--heatmap-stride`). The panel is a smooth field, not squares: one Gaussian splat per loaded taxel (`GLOW_TAXELS`, nothing below `SPLAT_FLOOR`), **blended with max, not sum**, so a taxel's peak stays exactly its own reading and falls off as a gradient — summing blew the contacts out into flat saturated blobs. Then a `FIELD_GAMMA < 1` lifts light contact into the visible bands without creating new saturation (the peak is already capped), and the thermal colormap tops out at a hot yellow, not white. `--heatmap-gain` scales raw counts before the ramp: VEGABAR 29's contact reads ~1500 counts against VEGABAR 38's saturating ~4094, so 29 looks cool unless you raise the gain. It is anchored inside `viewer.viewport`, not the window corner, so MuJoCo's own left UI panel doesn't cover it (press Tab to hide that panel). Regular Python draws it, and only the tactile sample runs under the viewer lock.
- The heat map's sensor layout (positions, palette) is copied from `hand_gui.py`, and its hand silhouette comes from `frontend/public/hand.png` (the PNG's alpha is fully opaque, so the outline is thresholded and flood-filled). The fill **must** be a morphological close (`SEAL_RADIUS`: dilate, fill, erode back): a plain fill leaks through breaks in the drawn outline and leaves the palm and parts of the fingers black. The layout is a hand-tuned approximation and the sim changes the pose, so a sensor patch can sit slightly off the drawn finger; that's the layout, not a bug.
- `generate_dataset.py` is the parallel version of `recorder.py` (`../venv/bin/python -m hand_sim.generate_dataset --episodes N --out ../models/dataset_sim --workers W`) — same session format, ~300 sessions in ~70 s, which is what `classifier/train_sim.py` trains on. `models/dataset_sim/` is generated output (90 MB, untracked); regenerate it rather than committing it.
- The viewer also overlays the live Sensor A/B estimate from `classifier/` next to the simulation's ground-truth object (`classifier_bridge.py`; `--no-classifier` to turn it off). The model variant comes from the `CLASSIFIER_SUFFIX` env var: `""` (real-data model), `"_sim"`, `"_combined"`. `run.py` defaults to `_combined` because the real-only model is confidently wrong on simulated tactile data; `hand_gui.py` defaults to `""` because it drives the real hand.

## Sensor classifier (`classifier/`)
- `train.py` / `predict.py` (teammate's, real data only) plus `train_sim.py` (sim data), `train_combined.py` (both), `evaluate_cross_domain.py` (cross-domain scores) and `model/xgb_sensor{, _sim, _combined}.pkl` with matching `scaler*` / `feature_cols*` (108 features, the tactile summary columns plus hand registers).
- Object labels: `vegabar_29` = Sensor A = 0, `vegabar_38` = Sensor B = 1 (`classifier_bridge.OBJECT_TO_LABEL`).
- Cross-domain failure is the main gotcha: the real-only model is ~chance on sim data, and the sim-only model scores ~29% on real data (worse than chance), because simulated tactile values, current and temperature are approximations. Don't read the combined model's 100% on its 4-session real holdout as a real result.
- The trustworthy real-data number is leave-one-session-per-class-out CV, ~89% per-frame and per-session. Real sessions carrying labels: `20261016_204344/204402/204429/204457/204513/204524/204548` (Sensor A) and `20261016_204558/204609/204619/204627/204637/204649` (Sensor B).
- `xgboost`, `scikit-learn`, `pandas` and `joblib` were installed into `venv/` by hand; they are not in `simulation/requirements.txt`.
